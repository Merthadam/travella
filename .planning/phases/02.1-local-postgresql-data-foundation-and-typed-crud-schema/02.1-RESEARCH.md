## Summary

The service already uses SQLAlchemy 2.x, psycopg 3, and Alembic dependencies, but the runnable Compose stack still sets `CRUD_DATABASE_URL` to SQLite and the CRUD process calls `Base.metadata.create_all()` at import time. The existing migrations also call `create_all()` instead of expressing schema operations, so they cannot enforce the requested migration boundary. The implementation should add a real Alembic environment, replace metadata auto-creation with a current-head check, and make Compose start a PostgreSQL service before CRUD. [VERIFIED: pyproject.toml:14-16] The declared ranges are `"sqlalchemy>=2.0,<2.1"`, `"psycopg[binary]>=3.2,<4"`, and `"alembic>=1.14,<2"`. [VERIFIED: compose.yaml:30-50] The current CRUD environment is `CRUD_DATABASE_URL: sqlite:////var/lib/travella/plans.sqlite3` and the health check calls `/ready`.

The model layer is already annotation-driven and has UUID primary-key annotations, timezone-aware `DateTime`, bounded string lengths, foreign keys, unique constraints, and lifecycle enums. [VERIFIED: services/crud/models.py:27-79] The main type gaps are PostgreSQL-specific JSONB for `PlanningBrief.payload` and receipt result data, explicit numeric precision/check constraints for coordinates, explicit bounded text for provider/external references, and migration-managed enum/check constraints. The repository currently serializes brief payloads with `json.dumps` and reads with `json.loads`; after JSONB mapping, it should pass dictionaries through SQLAlchemy and test native dict round-tripping. [VERIFIED: services/crud/repository.py:337-356] 

Use a PostgreSQL-specific SQLAlchemy URL in the form `postgresql+psycopg://user:password@host:port/dbname`; SQLAlchemy documents this dialect and the psycopg 3 driver separately from psycopg2. [CITED: https://docs.sqlalchemy.org/en/20/dialects/postgresql.html] Use `JSONB` for structured objects and a mutable wrapper only if the ORM must observe in-place dictionary edits; the current repository replaces payloads, so a plain `JSONB` column is sufficient for this phase. [CITED: https://docs.sqlalchemy.org/en/20/dialects/postgresql.html] Use named `CheckConstraint` objects for coordinate bounds and explicit `UniqueConstraint` names so Alembic can alter them deterministically. [CITED: https://docs.sqlalchemy.org/en/20/core/constraints.html]

**Primary recommendation:** convert the CRUD schema to explicit PostgreSQL SQLAlchemy types and hand-authored Alembic operations, run a dedicated PostgreSQL Compose service, and make CRUD startup compare Alembic database heads to script heads before serving traffic.

### Pattern 1: Explicit typed model columns

**What:** Use `Mapped[uuid.UUID]`, `Mapped[datetime]`, `Mapped[dict[str, object]]`, and `mapped_column` with explicit PostgreSQL `JSONB`, `UUID`, `DateTime(timezone=True)`, `Numeric`, and bounded `String` types. SQLAlchemy 2.x supports annotation-driven mappings and explicit type overrides. [CITED: https://docs.sqlalchemy.org/en/20/orm/declarative_tables.html]

**When to use:** Every durable field whose database representation is part of the contract, especially fields that must round-trip without string encoding or must be constrained server-side.

**Example:**

```python
from datetime import datetime
from decimal import Decimal
from uuid import UUID

from sqlalchemy import DateTime, Numeric, String
from sqlalchemy.dialects.postgresql import JSONB, UUID as PGUUID
from sqlalchemy.orm import Mapped, mapped_column

id: Mapped[UUID] = mapped_column(PGUUID(as_uuid=True), primary_key=True)
payload: Mapped[dict[str, object]] = mapped_column(JSONB, nullable=False, default=dict)
updated_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), nullable=False)
latitude: Mapped[Decimal] = mapped_column(Numeric(9, 6), nullable=False)
provider_id: Mapped[str] = mapped_column(String(255), nullable=False)
```

The exact precision and scale for coordinates must be locked in the implementation plan; PostgreSQL documents that `NUMERIC(precision, scale)` controls total digits and fractional digits, and rounds excess fractional digits. [CITED: https://www.postgresql.org/docs/17/datatype-numeric.html]

### Pattern 2: Database-enforced invariants plus API validation

**What:** Keep Pydantic bounds for friendly 422 responses and add named database checks for defense in depth. For example, `latitude BETWEEN -90 AND 90` and `longitude BETWEEN -180 AND 180`. PostgreSQL `CHECK` constraints reject rows that violate their Boolean expression. [CITED: https://www.postgresql.org/docs/16/ddl-constraints.html]

**When to use:** Any invariant that must hold if a caller bypasses FastAPI, during future migrations, or during background/agent writes.

**Example:**

```python
__table_args__ = (
    CheckConstraint("latitude >= -90 AND latitude <= 90", name="ck_destination_latitude"),
    CheckConstraint("longitude >= -180 AND longitude <= 180", name="ck_destination_longitude"),
)
```

### Pattern 3: Alembic is the only schema writer

**What:** Write migration operations explicitly (`create_table`, `add_column`, `alter_column`, `create_check_constraint`, and named indexes/constraints). Set Alembic `target_metadata` to `Base.metadata` for review/autogenerate support, but commit and review migration scripts as the authority. Alembic’s migration environment is maintained with the application source. [CITED: https://alembic.sqlalchemy.org/en/latest/tutorial.html]

**When to use:** Every schema change, including converting `Text` JSON to JSONB and adding coordinate checks.

### Pattern 4: Fail-fast current-head gate

**What:** At startup, open a connection and compare `MigrationContext.get_current_heads()` with `ScriptDirectory.get_heads()`. Alembic documents this comparison for branched revision trees and also provides `alembic current --check-heads` in recent versions. [CITED: https://alembic.sqlalchemy.org/en/latest/cookbook.html] [CITED: https://alembic.sqlalchemy.org/en/latest/api/commands.html]

**When to use:** Before constructing a serving app or reporting readiness. A missing `alembic_version`, a stale revision, or a failed connection must prevent `/ready` from passing.

### Pattern 5: Compose readiness and migration ordering

**What:** Define a PostgreSQL service with a health check using `pg_isready`; make migration and CRUD depend on `service_healthy`. Docker documents that Compose waits for dependencies marked `service_healthy` before creating dependents. [CITED: https://docs.docker.com/compose/how-tos/startup-order/]

**When to use:** Every local stack startup. A running container is not evidence that PostgreSQL is ready to accept SQL. [CITED: https://docs.docker.com/compose/how-tos/startup-order/]

### Anti-Patterns to Avoid

- **`Base.metadata.create_all()` in application startup:** it bypasses migration history and makes an unmigrated database appear valid. [VERIFIED: services/crud/server.py:23-24] The current source calls `Base.metadata.create_all(engine)`; remove this behavior from the serving path.
- **One migration calling `Base.metadata.create_all()`:** it cannot express alter/drop/constraint changes and cannot detect drift. [VERIFIED: services/crud/migrations/versions/0001_plan_lifecycle.py:11-16] The current migration calls `Base.metadata.create_all(bind=bind)` verbatim.
- **Leaving JSONB as `str`:** it forces repository encode/decode and makes native JSONB round-trip tests impossible. [VERIFIED: services/crud/models.py:121-128] The current `payload` annotation is `Mapped[str]` and its column is `Text`.
- **Porting SQLite SQL unchanged:** `INSERT OR REPLACE`, `?` placeholders, and SQLite-specific locking assumptions do not carry to PostgreSQL. [VERIFIED: services/auth/session_store.py:92-96] The auth store currently uses `INSERT OR REPLACE`; replace it with PostgreSQL upsert syntax through SQLAlchemy or an explicit `ON CONFLICT` operation.
- **Trusting Compose dependency order without health:** `depends_on` alone does not mean the database is ready; use `service_healthy`. [CITED: https://docs.docker.com/compose/how-tos/startup-order/]
- **Using floating image tags or printing database URLs:** pin the Postgres image and redact passwords from logs and verification artifacts. [ASSUMED]

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| PostgreSQL connectivity | Custom socket/connection protocol | SQLAlchemy `postgresql+psycopg` dialect | Handles DBAPI adaptation, pooling, transactions, and typed binding. [CITED: https://docs.sqlalchemy.org/en/20/dialects/postgresql.html] |
| Schema versioning | Startup `CREATE TABLE IF NOT EXISTS` | Alembic revision scripts and head comparison | Migration history and drift checks are the schema authority. [CITED: https://alembic.sqlalchemy.org/en/latest/tutorial.html] |
| JSON encoding | Manual string storage in `Text` | PostgreSQL `JSONB` through SQLAlchemy | Native structured values, operators, and server-side validation of JSON syntax. [CITED: https://docs.sqlalchemy.org/en/20/dialects/postgresql.html] |
| Invariant enforcement | Pydantic-only coordinate/enum checks | Pydantic plus named PostgreSQL constraints | Database constraints protect all writers and make invalid rows impossible. [CITED: https://www.postgresql.org/docs/current/ddl-constraints.html] |
| Compose readiness | `sleep` or fixed startup delays | Postgres healthcheck + `service_healthy` | Readiness is state-based rather than timing-based. [CITED: https://docs.docker.com/compose/how-tos/startup-order/] |
| Encrypted session payload protection | Plaintext cookie/session rows | Retain Fernet payload encryption, move rows to transactional PostgreSQL | Existing session contract encrypts payloads before persistence. [VERIFIED: services/auth/session_store.py:18-24] |

**Key insight:** the migration is a contract change across model typing, startup, Compose, and tests. Changing only `CRUD_DATABASE_URL` leaves silent `create_all()` behavior, text JSON, auth SQLite, and incomplete migration history in place.

## Common Pitfalls

### Pitfall 1: CRUD starts against an unmigrated database

**What goes wrong:** a new PostgreSQL volume starts empty and the server reports healthy because `create_all()` creates tables, or `/ready` only checks `SELECT 1 FROM plans`.

**Why it happens:** schema creation and readiness are currently coupled to metadata and do not inspect Alembic revision state. [VERIFIED: services/crud/server.py:23-24] [VERIFIED: services/crud/app.py:64-68]

**How to avoid:** run migrations as an explicit one-shot Compose service or command, then check current heads at application startup; `/ready` must include a migration gate.

**Warning signs:** no `alembic_version` row, current revision differs from script head, or CRUD can start after deleting the migration volume without running `alembic upgrade head`.

### Pitfall 2: JSONB conversion leaves double encoding

**What goes wrong:** the database stores a JSON string such as `"{...}"` rather than an object, or repository code calls `json.loads` on an already decoded dict.

**Why it happens:** `PlanningBrief.payload` is currently typed as `str`/`Text` and repository code explicitly dumps/loads it. [VERIFIED: services/crud/models.py:125-128] [VERIFIED: services/crud/repository.py:337-356]

**How to avoid:** change the model type to `dict[str, object]`/JSONB, assign dictionaries directly, and assert with a raw SQL or ORM read that the result is a dict.

**Warning signs:** returned ORM values have type `str`, stored JSON begins and ends with quotes, or update code serializes twice.

### Pitfall 3: PostgreSQL stricter types expose SQLite-only assumptions

**What goes wrong:** tests pass with SQLite but fail under PostgreSQL because SQLite ignores some constraints/types, differs in locking/upsert semantics, or returns naive timestamps.

**Why it happens:** existing tests create an in-memory SQLite engine and call `Base.metadata.create_all()`. [VERIFIED: services/crud/tests/conftest.py:10-16] [VERIFIED: services/crud/tests/test_api.py:46-48]

**How to avoid:** use an isolated PostgreSQL database for the HTTP integration fixture and retain only focused unit tests on SQLite if they do not assert database-specific behavior. Run migrations in the fixture before the TestClient uses the app.

**Warning signs:** the test suite has no PostgreSQL service, no migration step, or uses SQLite-only SQL in repository/auth persistence.

### Pitfall 4: Numeric bounds exist only in Pydantic

**What goes wrong:** direct SQL or future agent/service writes can persist invalid coordinates.

**Why it happens:** the API schema has `Field(ge=-90, le=90)` and `Field(ge=-180, le=180)`, but the model uses unconstrained numeric inference and no checks. [VERIFIED: services/crud/schemas.py:101-107] [VERIFIED: services/crud/models.py:112-118]

**How to avoid:** add explicit numeric precision/scale and named database checks, then test constraint failure through a database transaction.

### Pitfall 5: Auth session migration is silently omitted

**What goes wrong:** Plans use PostgreSQL but auth refresh, recovery-code consumption, and session invalidation remain tied to a local SQLite file.

**Why it happens:** `SessionStore` is a direct sqlite3 implementation and Compose supplies `SESSION_DB_PATH`. [VERIFIED: services/auth/session_store.py:18-32] [VERIFIED: compose.yaml:7-16]

**How to avoid:** include auth session tables in the same PostgreSQL migration boundary or define a separately versioned auth schema using the same PostgreSQL service; preserve Fernet encryption and transactional semantics.

### Pitfall 6: Migration scripts are not reversible or deterministic

**What goes wrong:** downgrade is a no-op, migration ordering is implicit, or a migration depends on current model metadata rather than the historical schema.

**Why it happens:** current `0002` and `0003` downgrades are `pass`, while upgrades call current metadata. [VERIFIED: services/crud/migrations/versions/0002_destination_pins.py:12-21] [VERIFIED: services/crud/migrations/versions/0003_planning_briefs.py:11-17]

**How to avoid:** write explicit `op.create_table`/`op.drop_table`/`op.alter_column` operations and name every constraint; test upgrade from base and downgrade where the phase requires it.

## Code Examples

### PostgreSQL engine URL

```python
from sqlalchemy import create_engine

engine = create_engine(
    "postgresql+psycopg://travella:password@postgres:5432/travella",
    future=True,
    pool_pre_ping=True,
)
```

SQLAlchemy documents `postgresql+psycopg://` as the psycopg 3 connection form. [CITED: https://docs.sqlalchemy.org/en/20/dialects/postgresql.html]

### Current-head check

```python
from alembic.migration import MigrationContext
from alembic.script import ScriptDirectory

with engine.connect() as connection:
    current_heads = set(MigrationContext.configure(connection).get_current_heads())
    expected_heads = set(ScriptDirectory.from_config(alembic_config).get_heads())
    if current_heads != expected_heads:
        raise RuntimeError("Database migrations are not at the expected head")
```

Alembic documents `MigrationContext.get_current_heads()` and comparison with `ScriptDirectory.get_heads()` for checking a database against a revision tree. [CITED: https://alembic.sqlalchemy.org/en/latest/cookbook.html]

### JSONB model and direct dictionary repository assignment

```python
from sqlalchemy.dialects.postgresql import JSONB

payload: Mapped[dict[str, object]] = mapped_column(JSONB, nullable=False, default=dict)

row.payload = data
session.add(row)
```

SQLAlchemy’s JSONB documentation describes direct dictionary inserts and warns that in-place mutation requires the mutable extension; replacing the dictionary avoids that need for the current repository. [CITED: https://docs.sqlalchemy.org/en/20/dialects/postgresql.html]

### Compose database readiness

```yaml
postgres:
  image: postgres:<pinned-version>
  environment:
    POSTGRES_DB: travella
    POSTGRES_USER: travella
    POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set in .env}
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
    interval: 5s
    timeout: 3s
    retries: 12

crud:
  depends_on:
    postgres:
      condition: service_healthy
```

Docker’s official Compose guidance uses `pg_isready` and `service_healthy` to wait for PostgreSQL readiness. [CITED: https://docs.docker.com/compose/how-tos/startup-order/]

## Open Questions

All questions below are resolved for this phase; the decisions are recorded here so implementation does not reopen them.

1. **Should auth session tables be in the CRUD Alembic migration environment or a separate auth migration environment?**
   - What we know: the phase explicitly says PostgreSQL is the only local Compose database for Plans and auth sessions, while the current auth store is a direct SQLite implementation. [VERIFIED: 02.1-CONTEXT.md] [VERIFIED: services/auth/session_store.py:18-32]
   - What’s unclear: service ownership and whether the auth service should own a separate schema/version table.
   - **RESOLVED:** use one shared Alembic migration environment and revision chain for the local database, while keeping auth tables clearly auth-owned by naming and service boundaries. The shared chain runs before both services start.

2. **What PostgreSQL major image should local Compose pin?**
   - What we know: Docker Compose needs a pinned image and a readiness check; no version is currently specified. [VERIFIED: compose.yaml:1-67]
   - What’s unclear: the project has not locked a supported Postgres major.
   - **RESOLVED:** pin local Compose to PostgreSQL 17 (minor tag may be tightened in implementation) and use the same image for integration verification.

3. **What is the exact coordinate precision?**
   - What we know: API bounds are latitude `-90..90` and longitude `-180..180`. [VERIFIED: services/crud/schemas.py:101-107]
   - What’s unclear: precision/scale for storage and whether six decimal places is the product requirement.
   - **RESOLVED:** use `NUMERIC(9,6)` for latitude and longitude, with named database checks for the API bounds and boundary tests.

4. **How should the SQLite-to-PostgreSQL local reset be communicated?**
   - What we know: current local data is in named Docker volumes and the new stack will use a PostgreSQL volume. [VERIFIED: compose.yaml:22-23,44-67]
   - What’s unclear: whether developers need a one-time data export.
   - **RESOLVED:** local SQLite data is not imported automatically; document `docker compose down -v` as the explicit clean reset for this local-only phase. Any import utility is deferred.

### Known Threat Patterns for PostgreSQL CRUD

| Pattern | STRIDE | Standard Mitigation |
|---|---|---|
| SQL injection via migration or repository string interpolation | Tampering | Use SQLAlchemy expressions/bound parameters; keep raw SQL limited to fixed named checks and health queries. |
| Cross-traveler row access | Information disclosure | Filter every CRUD read/mutation by token-derived subject and test foreign identity through HTTP. [VERIFIED: docs/skills/travella-testing/SKILL.md] |
| Unencrypted auth session payloads | Information disclosure | Preserve Fernet encryption before insert/update and exclude secrets from logs/evidence. [VERIFIED: services/auth/session_store.py:3-4] |
| Serving with stale schema | Tampering/availability | Fail closed when current Alembic heads do not match script heads. [CITED: https://alembic.sqlalchemy.org/en/latest/cookbook.html] |
| Password leaked in connection URL/logs | Information disclosure | Inject connection URL through ignored environment/secret configuration and redact URL on errors. [ASSUMED] |

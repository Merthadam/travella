<interfaces>
Register account routes through register_account_routes(app, provider, verifier, store, current_session, ready, clock, capability_reader) in new account.py; preserve existing cookie/CSRF/body/rate/error middleware. Inject a read-only capability reader for tests; default provider reader uses DescribeUserPool, DescribeUserPoolClient and GetUserPoolMfaConfig with bounded calls/cache. Failure gives unavailable, never a permissive default. No new package, migration, AWS policy or pool change.

GET /auth/account returns {identity:{first_name,last_name,email,email_verified}, capabilities:{email_change:{available,reason},password_change:{available,reason},authenticator:{setup,replace,disable,reason},recovery_codes:{rotate,reason}}, password_policy:{minimum_length,require_uppercase,require_lowercase,require_numbers,require_symbols}|null, mfa:{status:on|off|unavailable}, recovery_codes:{status:available|empty|unavailable,remaining:integer|null}, pending_email:null|{operation_id:string|null,new_email:string|null,state:awaiting_verification|reconciliation_required,resumable:boolean}}. Ordinary responses never contain token, subject, provider Username, secret, code hashes or proof. Canonical email appears only here/private explicit email responses, never memory/URLs/logs. Unknown operation capability must not block preferences or name reads.

PATCH /auth/account/name accepts {first_name,last_name,expected_names:{first_name,last_name},event_id:UUID}; nonempty trimmed names max 128; response is AccountOutput above. Under subject lock compare provider's current names to expected_names unless the event was already acknowledged; conflict returns 409 account_conflict. Replay digest protects changed bodies; readback must match requested values.

POST /auth/account/verification accepts {purpose:email_change|password_change|mfa_setup|mfa_replace|mfa_disable|recovery_rotate,password:SecretStr}. Returns {state:verified|mfa_required,verification_id,expires_in:300}. POST /auth/account/verification/complete accepts {verification_id,code}; returns verified only after a valid same-subject Cognito TOTP response. A proof is bound to subject, current sid digest and purpose, single-use, expires after 300s and cannot outlive the original session. Only these explicit states advance UI.

POST /auth/account/email/start accepts {new_email,verification_id,event_id:UUID}; response {state:awaiting_verification,operation_id,account:AccountOutput}. POST /auth/account/email/resend accepts {operation_id}; returns {state:awaiting_verification}. POST /auth/account/email/verify accepts {operation_id,code:SecretStr}; returns {state:complete,account:AccountOutput} only after verified exact new email and local reconciliation. GetUser supplies pending intent readback via GET account; cancellation leaves the editor without claiming provider-code revocation. Replaced/expired/noninitiating-session operations return 409 obsolete_operation or 403 verification_required.

Account errors: 400 verification_failed|invalid_code|password_policy; 403 verification_required; 409 account_conflict|request_reused|obsolete_operation|operation_pending; 422 invalid_account; 429 rate_limited; 503 capability_unavailable|provider_unavailable|result_unknown. Shape {code,message,fields?} has allow-listed field names and safe copy, never submitted values. Only invalid/expired actual session is 401 and clears the cookie; wrong verification must not sign the traveler out.

Encrypted account operation records reuse auth_sessions with kind=account_operation, subject, owner_sid_hash, purpose, event_id, request_digest, status and expiry; generated opaque record IDs are short-lived proofs/operation IDs. Never store passwords. Persist provider tokens only inside the existing encrypted boundary when needed for a challenge, then revoke/discard them. Add subject account_guard: PostgreSQL advisory session lock held across journal/provider/reconciliation stages, SQLite process lock under the existing single-worker limitation. Individual journal/store transactions commit at stage boundaries; an external provider success cannot be rolled back by SQL rollback. Expired records are cleaned by existing store expiry. Concurrent sessions cannot replace a pending subject email intent silently.

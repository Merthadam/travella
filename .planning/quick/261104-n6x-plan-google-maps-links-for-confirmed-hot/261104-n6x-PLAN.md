# Confirmed checkout locations on the Travella map

## Agreed scope

After confirmed checkout, let the traveler add the accommodation or airport to the map inside Travella. The user chose planning without interactive prototypes and clarified that places will likely already exist on the map. Resolve existing places before offering a new pin. This planning task was subsequently implemented in quick task 261104-nc5 after explicit user approval.

Current checkout is explicitly sandbox/test-only. Retain that distinction throughout this feature. Payment completion alone is insufficient: use the existing provider-confirmed result. This plan does not expand real booking authority.

## Proposed journey

Add a compact “Your trip map” section to the shared confirmation actions panel. Keep the existing receipt, return-to-trip action and download actions.

For each location, show its name and address or airport name/code, followed by one action:

| State | Action/result |
|---|---|
| Exact location already saved | “View on trip map”; navigate to the map, reveal and select the existing pin |
| Exact location in the current unsaved draft | “Saving to trip map…”; reflect the existing save result without inserting another pin |
| Location absent, reliable coordinates available | “Add to trip map”; this explicit click confirms the displayed place |
| Similar existing pin, identity uncertain | “Review matching place”; show the existing and provider location for the traveler to choose |
| Save in flight | Disable repeated add; show “Saving…” |
| Save acknowledged | “Added to trip map” and “View on trip map” |
| Save failed/conflicted | Explain that it is not saved; offer existing retry/review flow |
| Location missing or ambiguous | “Location unavailable”; allow existing manual map search without guessing coordinates |
| Map at 50-pin limit | Existing pins remain viewable; new additions explain the limit and link to the map |

Stay confirmation shows the booked property. Proposed flight scope: destination arrival airport and, if different, the airport used to depart that destination on the return journey. Derive both from actual itinerary segments; exclude connection airports and the home airport by default. The user approved this plan for implementation, including this flight scope.

Clicking View opens the existing map/list state and selects the pin, including when a category filter currently hides it. On mobile, reveal its place card without covering the selected marker. Adding stays on the confirmation screen; navigation remains explicit. Map-provider failure leaves the saved place accessible in List view.

## Implementation sequence

### 1. Preserve usable checkout locations

Carry a validated optional hotel coordinate pair from the selected property through checkout state, confirmed reservation and persisted booking projection. Bind it to the same hotel ID. Audit every state reconstruction so refresh/prebook cannot drop it. When absent, use the existing private Connector hotel-details operation for that exact hotel ID; expose only normalized location fields. An unavailable lookup must not block booking confirmation or fabricate a pin.

For airports, resolve actual confirmed itinerary endpoints against the shared airport catalogue through an existing reference-data boundary where available. Avoid bundling the entire catalogue into the checkout component. Record whether data came from provider property details or the airport catalogue; never copy guest details, references or payment information into a map pin.

Old saved bookings remain readable. Hotel address-only records use an exact hotel-details lookup where possible; otherwise offer manual location selection. Old flights without sufficiently specific itinerary evidence show unavailable rather than assuming a city code is an airport.

Completion: fresh confirmation, refresh and reopened booking produce the same eligible location identities and positions; missing data remains explicit.

### 2. Resolve existing pins before offering Add

Use stable source identities: LiteAPI property ID and actual airport IATA code. Persist optional source identity on the pin so an existing Google-backed pin can also be associated with the confirmed property/airport after traveler confirmation. Preserve its existing ID, position and Google details. Update the strict frontend, CRUD and agent projection contracts together; legacy pins remain valid.

Resolution order:
1. Exact source identity already attached to a saved/draft pin: reuse it.
2. Exact verified Google Place ID shared by both records: reuse it.
3. Legacy pin with compatible category, similar name/address and nearby coordinates: present a possible match for explicit review. Proximity/name alone never silently merges pins, especially hotels in the same building or airport terminals.
4. No match: create a deterministic provider-scoped ID within current ID constraints, keeping source identity separate from any Google Place ID.

The review identifies the exact existing pin to associate. It may instead offer “Add as a separate place” with the provider location shown. Association is a durable mutation and requires the traveler's explicit action. Do not overwrite an existing edited position or description as a side effect. A verified identity with differing coordinates stays linked to the existing pin; offer a separate reviewed location edit if needed.

Re-read the current map when executing the action. Guard duplicate clicks, concurrent checkout callbacks, reloads, and multiple tabs. Validate unique IDs and unique provider identities in the durable contract. A stale revision follows the existing conflict flow; do not overwrite unrelated pins or silently retry an obsolete whole snapshot.

Completion: an already saved hotel/airport is focused without inserting another pin; uncertain matches require a choice; repeated additions yield one pin.

### 3. Wire confirmation actions and durable save

Pass eligible locations, saved/draft pin resolution and callbacks through PlanningCanvas into both checkout confirmations and the shared actions component. Add a dedicated canvas action for confirmed locations with explicit outcomes; generic `action()` currently may silently return when busy and is insufficient as an acknowledged result.

Serialize with existing booking autosave. The traveler sees the exact place before clicking Add; save the resulting complete consistent snapshot using the existing revision/idempotency contract. Treat the pin as saved only when the acknowledged snapshot contains that identity. Keep booking-save errors and pin-save errors understandable. Do not add on payment callbacks, component mounting, confirmation polling, reopening or agent generation.

Implement View navigation through the existing map selection/filter state. Respect Plan switching/unmount guards so a late lookup or save cannot affect another Plan. Removing a pin uses the current explicit map remove flow; a later revisit can offer Add again. Cancellation or booking changes never silently remove previously saved places.

Completion: explicit Add persists once; View consistently selects the right existing/new pin after reload; automatic checkout transitions do not create pins.

### 4. Verification gate

Before implementation, capture the intended layout and current confirmation/map screens using Chrome DevTools. The original browser profile blocker was resolved with isolated Chrome DevTools; see the completed evidence record.

Focused frontend coverage: exact existing match, legacy possible match selection, no match, repeat click, save acknowledgement/error/conflict, busy booking save, missing/invalid coordinates, pin limit, category filters, Plan switching, reopened booking and airport selection from multi-segment itineraries.

Connector/model coverage: hotel ID binding, coordinate validation including valid zero values, checkout state reconstruction, missing hotel details, and old saved documents.

Exercise changed CRUD save/read behavior through FastAPI with a test database: add/read back, associate existing/read back, duplicate identity rejection, revision conflict, ownership/unauthenticated cases, unrelated fields preserved, remove/reload and recovery lifecycle. Extend existing canvas and stay-reservation integration coverage rather than relying on mocks.

Authenticated browser gate: use the designated example account, create isolated test Plans, exercise both sandbox confirmation paths and reopen them. Verify existing-pin View, missing-pin Add, uncertain match choice, reload persistence, failed save retry, list fallback and desktop/mobile layouts. Inspect console/network and saved screenshots; clean up only records created for this verification.

Use repository scripts discovered in `frontend/package.json` (Vitest and build); local app startup is `bash scripts/start-local-ready.sh`, with the local skill's prechecks. Default documented origin is `http://localhost:5174`; verify the actual running origin before use. No application test runs were executed during this planning session.

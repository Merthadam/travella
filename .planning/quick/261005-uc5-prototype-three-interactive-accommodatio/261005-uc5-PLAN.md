# Planning card design exploration

Question: how should accommodation and return-flight A2UI cards look and feel in the planning canvas?

User chose three interactive alternatives. Scope is throwaway design, not production A2UI or provider wiring.

- Prototype branch: prototype/planning-cards. Mount inside the existing authenticated Plans shell, gated by development mode and `?prototype=travel-cards&variant=A|B|C`.
- A: visual browse cards; B: comparison rows; C: combined trip board with replaceable stay/flight slots.
- Use fictional offers and in-memory shortlist/compare/details state. Show all relevant prototype state and explicit sample-price notices. No Plan/profile/booking mutations.
- Start a dedicated localhost development preview through a single npm command. Inspect each direction with Chrome DevTools, exercise details/shortlist/compare and mobile layout; capture screenshots and inspect console/network. No automated tests or model calls.
- Keep prototypes on this branch. User selection is pending; production implementation and schemas follow discussion.

## Accepted steering during exploration

The user changed the canvas design to small entry containers, with full results on dedicated Flights/Accommodation views. Both containers should be agent-generatable. Revised alternatives: A tiles, B rows, C journey sequence. Generation is simulated for design review; production integration remains out of scope.

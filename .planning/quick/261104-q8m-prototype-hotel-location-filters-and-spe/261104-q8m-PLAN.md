# Flexible hotel location search

User requests location-aware accommodation reasoning plus manual Booking-style filters, and explicitly selected three interactive prototypes before production design selection. Any combination of saved places or categories must be selectable. Flights are outside scope.

1. Trace current hotel criteria, provider adapter, shared workspace and specialist reasoning. Specify a shared, evidence-backed proximity contract and acceptance criteria.
2. Build three throwaway interactive variants on the existing authenticated Plan accommodation surface. Preserve real app shell/read context; all prototype filters, hotel results, map and assistant actions are simulated and in memory. Include city center, landmarks, arbitrary multi-place/category selection, radius/preference distinction, empty states, and manual/assistant synchronization.
3. Exercise all variants with Chrome DevTools; capture and inspect desktop/mobile screenshots and console/network checks. Present previews and followups. Record selection before production implementation.

## Acceptance criteria
- Location preferences visible and editable through manual controls and simulated assistant proposals.
- Select/deselect individual places and categories, including overlapping category membership without duplicate scoring; choose any subset of available saved places.
- Support named city-center anchor and landmark, flexible proximity ranking, optional strict radius to every selected place.
- Show honest straight-line distance labels, missing-coordinate handling and no-match recovery; do not invent walking times.
- No durable Plan mutation, provider search, booking or real agent request from prototype controls.
- Three structurally distinct alternatives, URL variant switching and keyboard navigation, desktop/mobile evidence.
- Production spec includes normalized criteria, authoritative anchor resolution, deterministic scoring, provider call bounds, staleness/revision protection, and end-to-end checks.
